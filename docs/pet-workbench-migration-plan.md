# 桌宠信息卡：原管理页面逐步迁移计划

> 状态：已纠正迁移目标：原管理功能要在桌宠弹出的信息卡内直接使用；完整功能面板已接入，手动交互验收待完成（2026-10-25）。
> **迁移期间保留全部原管理页面；未经用户明确要求，不删除旧页面、旧导航入口或其功能。**

## 1. 目标与范围

桌宠成为日常入口。用户点击桌宠打开信息卡，并在这个窗口内直接查看活动、会话、供应商
和其他管理能力。现有八个顶级管理页面按顺序迁移到桌宠信息卡；卡内操作复用现有领域层，
原管理页面继续保留并可正常操作。迁移完成也不自动触发删除，旧界面何时退役由用户另行决定。

“桌宠里的页面”分成三层，完整管理内容放入桌宠弹出的可调整大小信息卡：

1. **桌宠本体**：桌面常驻、活动状态、收起/唤回和少量即时操作。
2. **信息卡**：桌宠的主要操作窗口，默认 1080×720、最小 800×600；首页保留最近活动、
   Agent 概况和最近结果，八个管理区在同一窗口内提供完整列表、表单和历史详情。
3. **控制中心**：主窗口原有八个管理页面及莲花导航继续保留，作为并行入口。

信息卡内的管理内容复用现有页面组合与应用服务，不改变持久化格式、配置写入、路由行为、
备份规则或数据目录。卡片内选择管理区时只更新信息卡内容，不打开另一个管理窗口。

## 2. 必须遵守的迁移规则

- **旧页面保留**：旧页面、旧导航及旧操作在每个迁移阶段都继续工作。不得以迁移为由
  删除页面、隐藏入口、删减功能或清理相关代码。之后只有用户明确要求时，才另行评估
  旧页面退役。
- **共用领域实现**：桌宠信息卡复用现有 `ProviderStore`、`LocalRouter`、MCP、Skills 和
  sessions 模块。迁移 UI 不复制写入逻辑，不形成两份配置状态。
- **逐页验收**：每个页面单独标记状态。新入口完成对应页面的主要查看和操作、错误与
  加载状态验证，并确认旧页面仍可用后，才把该页标成已迁移。
- **过程可回退**：新入口出问题时仍可通过旧页面完成管理。阶段之间不要求配置迁移，
  不做可能丢失用户数据的自动清理。
- **桌宠仍轻量**：桌宠本体保持小而常驻；大列表和完整表单进入可调整大小的信息卡。文件扫描、导入、
  导出、删除等沿用现有 Worker 与确认流程。
- **隐私边界不变**：不增加屏幕、前台窗口、剪贴板或会话正文的桌宠采集；活动状态仍只
  使用明确启用的来源和现有本地数据。

## 5. 共通验收条件

每个迁移页面至少满足以下条件，才可标记“已迁移”：

1. 旧页面已有的主要查看与操作都能在桌宠信息卡中完成，且不会意外省略成熟能力。
2. 读写使用原来的领域模块、Store 和持久化契约；从任一入口修改后另一入口能看到同一状态。
3. 加载、空状态、未知状态、失败反馈、取消和重复触发行为清楚；文件 IO 沿用 Worker。
4. 信息卡可从桌宠直接打开，关闭或返回不丢桌宠位置、外观、启动偏好或托盘状态。
5. 原管理页面仍能到达并完成相同操作；迁移不触发旧页面删除或不可逆数据变更。
6. 对领域行为变化补相应测试；完成项目要求的构建、测试、diff 检查与提交流程。
